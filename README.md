# Приказ

**PAMS — Project & Attestation Management System.**
Система управления проектами и аттестацией для колледжа.

Приказ — не LMS и не CRM. LMS управляет контентом (курсы, уроки, тесты) — здесь контента нет, есть проекты. CRM управляет отношениями с клиентами — здесь не клиенты, а студенты и проекты. Приказ ближе к PPM (Project Portfolio Management) в корпоративном мире, но со спецификой учебного процесса: журнал, оценки, проектная работа, разграничение доступа к персональным данным.

Расшифровка названия:

| Буква | Слово | Что в системе |
|---|---|---|
| П | Проекты | Реестр студенческих проектов, фазы, типы (оригинал/форк) |
| Р | Регламенты | Workflow фаз, правила переходов |
| И | Инструменты | Журнал, модалка оценок, встроенная справка |
| К | Контроль | Статусы проектов, комментарии преподавателя |
| А | Аттестация | Оценки, посещаемость, сводка по курсу |
| З | Защита | Роли, разграничение доступа, ПДн только здесь |

**Статус: апробация, не готовое решение.** Требования меняются по результатам следующей недели. Если что-то в этом README расходится с реальностью — права реальность.

---

## Назначение

Приказ решает две задачи:

1. **Убрать персональные данные из репозиториев.** В Gogs и GitHub — только псевдонимы `s-<группа>-<номер>`. Всё, что идентифицирует студента (ФИО, группа, оценки, согласия), — только в Приказе. Это требование 152-ФЗ, не удобство.
2. **Вести учебный процесс в одном месте:** журнал с оценками, комментарии преподавателя, видимость для родителей, проектная работа, аттестация.

---

## Роли

| Роль | Что делает |
|---|---|
| **Администратор** | Единственный, кто создаёт пользователей. Управляет уроками, проектами, привязкой родителей к студентам. Видит аудит. |
| **Преподаватель** | Ведёт журнал (ставит оценки и заметки), меняет фазы проектов, видит сводку по курсу и активность родителей. |
| **Студент** | Видит свои оценки, заметки преподавателя, свои проекты и их фазы. |
| **Родитель** | Видит журнал и проекты только своего ребёнка. Факт его захода фиксируется и виден преподавателю. |

Самостоятельной регистрации нет. Пользователей создаёт администратор через раздел «Пользователи».

## Что уже работает

**Журнал.**
Сетка «студенты × занятия». Клик по ячейке открывает модалку: отметка (5/4/3/2/н/·) и заметка. Заметка видна студенту и родителю. Клик по дате — тема урока и домашнее задание.

**Проекты.**
Реестр проектов с фазами (Выбор темы → Работа → Предварительная защита → Защита). Типы: оригинал, форк, исследование, интерактив, доклад. У проекта — участники, история фаз, ссылка на репозиторий. Над одним проектом может работать несколько студентов, у одного студента — несколько проектов.

**Админка.**
- Пользователи: создание, деактивация, сброс пароля.
- Студенты: ФИО, группа, псевдоним.
- Родители: привязка к студентам.
- Уроки: номер, дата, тема, домашнее задание. CRUD.
- Проекты: создание, участники, тип, ссылка на репозиторий.
- Аудит: последние 100 действий (login, оценки, фазы, действия админа) с IP.

**Встроенная справка.**
Плавающая «?» в правом нижнем углу, статьи по роли, feedback под каждой статьёй.

**Безопасность (см. раздел отдельно).**
Хэширование паролей, CSRF на всех POST, аудит, сессионные cookie `httponly`/`samesite`, БД вне webroot.

## Структура

```
/home/<user>/                          ← владелец сайта
├── prikaz-data/                       ← НЕ доступен по HTTP (на уровень выше сайта)
│   ├── config.php                     ← конфиг: пути, имя сессии, пароль-минимум
│   ├── prikaz.sqlite                  ← БД (создаётся db/init.php)
│   └── storage/                       ← на будущее
└── steelfeet.ru/                      ← DocumentRoot сайта
    └── prikaz/
        ├── .htaccess                  ← блокирует lib/ и db/, кроме init.php
        ├── index.php                  ← единственный PHP, доступный по URL
        ├── assets/
        │   ├── styles.css             ← базовая типографика
        │   ├── prikaz.css             ← стили интерфейса
        │   ├── common.js              ← cookie-баннер
        │   └── teacher.js             ← модалка оценок
        ├── lib/
        │   ├── .htaccess              ← Require all denied
        │   ├── bootstrap.php          ← PDO, сессия, CSRF, auth, аудит
        │   ├── utils.php              ← e(), redirect, flash, asset_url
        │   ├── journal.php            ← агрегаты оценок
        │   ├── projects.php           ← фазы, история
        │   ├── data.php               ← загрузка данных для рендера
        │   ├── actions.php            ← все POST-обработчики
        │   └── views/                 ← шаблоны по ролям
        └── db/
            ├── .htaccess              ← временно разрешает init.php
            └── init.php               ← инициализация БД (CLI + HTTP)
```

Ключевое: **`config.php` и `prikaz.sqlite` лежат физически вне DocumentRoot.** Веб-сервер не отдаст их ни при каких условиях. Даже если DocumentRoot случайно настроят на корень сайта — сработает `.htaccess` с `RewriteRule ^prikaz-data(/|$) - [F,L]`.

## Установка

### 1. Создать `prikaz-data/` и `config.php`

На уровень выше корня сайта:

```bash
mkdir -p /home/<user>/prikaz-data
chmod 775 /home/<user>/prikaz-data
```

`/home/<user>/prikaz-data/config.php`:

```php
<?php
declare(strict_types=1);

return [
    'app_name'         => 'Приказ',
    'db_path'          => __DIR__ . '/prikaz.sqlite',
    'storage_path'     => __DIR__ . '/storage',
    'session_name'     => 'prikaz_session',
    'session_lifetime' => 86400 * 7,
    'password_min'     => 8,
    'csrf_key'         => 'prikaz_csrf_token',
];
```

### 2. Загрузить файлы `prikaz/` в корень сайта

Итоговый путь: `/home/<user>/steelfeet.ru/prikaz/`.

### 3. Проверить права на запись

```bash
# Владелец должен совпадать с пользователем веб-сервера
ls -la /home/<user>/prikaz-data/
```

Если PHP-FPM работает от `www-data`, а папка принадлежит `user` — либо `chown www-data:www-data`, либо `chmod 775` + `usermod -a -G user www-data`. На shared-хостинге обычно это уже решено, но проверить надо до первого запуска.

### 4. Инициализировать БД

Открыть в браузере: `https://steelfeet.ru/prikaz/db/init.php`

Файл покажет ход инициализации, сводку по таблицам и учётные данные администратора. Пароль зашит константой в `init.php` — **смени его перед деплоем** или смени через раздел «Профиль» сразу после первого входа.

Альтернативно — из CLI:

```bash
php /home/<user>/steelfeet.ru/prikaz/db/init.php
```

Если путь к конфигу определяется неправильно:

```bash
PRIKAZ_CONFIG=/home/<user>/prikaz-data/config.php php prikaz/db/init.php
```

### 5. Закрыть `init.php`

**Это не опциональный шаг.** После инициализации `init.php` больше не нужен, но содержит пароль администратора. Закрой его одним из способов:

- Удалить файл: `rm /home/<user>/steelfeet.ru/prikaz/db/init.php`
- Вернуть в `prikaz/db/.htaccess` строку `Require all denied` без исключений
- Вернуть в `prikaz/.htaccess` правило `RewriteRule ^db/ - [F,L]` (без `?!init.php$`)

### 6. Войти и сменить пароль

`https://steelfeet.ru/prikaz/index.php?page=login` → «Профиль» → «Сменить пароль».

### 7. Создать первых пользователей

От имени администратора:

1. Раздел «Пользователи» → преподаватель.
2. Раздел «Пользователи» → студенты (ФИО, группа, псевдоним).
3. Раздел «Пользователи» → родители.
4. Раздел «Родители» → привязать родителя к студенту.
5. Раздел «Уроки» → добавить занятия.
6. Раздел «Проекты» → создать проекты и назначить участников.

После этого преподаватель может ставить оценки, студенты и родители — видеть результат.

## Безопасность

| Механизм | Реализация |
|---|---|
| Пароли | `password_hash(PASSWORD_DEFAULT)`, авторехэш при входе |
| CSRF | Токен в сессии на всех POST-формах, `hash_equals` при проверке |
| Сессия | `session_regenerate_id` при входе, `httponly`, `samesite=Lax`, `secure` при HTTPS |
| SQL | Только подготовленные запросы |
| XSS | Все выводы через `e()` (`htmlspecialchars` с `ENT_QUOTES`) |
| Аудит | Все действия (login, оценки, фазы, действия админа) с IP и временем |
| Разграничение | Роль проверяется на каждом POST и каждой странице |
| БД | Физически вне webroot; `.htaccess` дополнительно блокирует `lib/`, `db/`, `prikaz-data/` |
| `init.php` | Одноразовый; после инициализации закрывается вручную |

**Что не реализовано:**

- Восстановление пароля по email — нет SMTP, пароль сбрасывает админ.
- Ограничение попыток входа (rate limiting) — не сделано. Если понадобится, ставится на уровне nginx/Apache.
- Двухфакторная аутентификация — не планируется в текущей апробации.
- 152-ФЗ в полном объёме — соблюдается на уровне «ПДн не покидают Приказ», но формального согласия на обработку ПДн в интерфейсе нет. Это отдельная задача.

## Соответствие 152-ФЗ

Требование: **ПДн не попадают в репозитории.**

Сделано:
- В Gogs/GitHub — только псевдонимы `s-<группа>-<номер>`.
- В Приказе — таблица `students` с полями `full_name`, `group_name`, `alias`. Расшифровка «псевдоним → ФИО» видна только ролям с доступом (админ, преподаватель).
- Все действия с ПДн (вход, оценки, смена фаз) попадают в `audit_log` с IP и временем.

Не сделано:
- Формальное согласие на обработку ПДн (чекбокс при первом входе родителя или студента).
- Выгрузка «все данные по мне» — нет endpoint для этого.
- Удаление данных по требованию — только через `DELETE FROM students` вручную.

Для колледжа этого достаточно на этапе апробации. Для вуза — надо доработать.

## Развёртывание в папке (без поддомена)

Subdomain не всегда возможен (тарифы хостинга, DNS-ограничения). Приказ разворачивается в папке `prikaz/` внутри сайта, но конфиг и БД — на уровень выше. Это компенсирует меньшую изоляцию.

Если сайт на Apache, `.htaccess` в `prikaz/` уже блокирует `lib/` и `db/`. Дополнительно стоит проверить, что `DocumentRoot` сайта не указывает на `/home/<user>/` (родительскую папку) — иначе `prikaz-data/` станет доступен.

Если сайт на nginx, `.htaccess` игнорируется. Нужно прописать в конфиг сервера:

```nginx
location ^~ /prikaz/lib/  { deny all; return 403; }
location ^~ /prikaz/db/   { deny all; return 403; }
location ^~ /prikaz-data/ { deny all; return 403; }
location ~ ^/prikaz/.*\.(sqlite|sqlite-wal|sqlite-shm|md|log)$ { deny all; return 403; }
```

`init.php` на nginx временно открывается через `location = /prikaz/db/init.php { ... }` или через исключение в `deny`.

## Что не реализовано

- **Самостоятельная регистрация** — только через админа. Это фича, не баг.
- **Массовый импорт пользователей** — CSV/Excel. Пока вручную через админку.
- **Экспорт журнала** — не сделано. Планируется XLSX.
- **Согласование `methodology` (Листа спецификации)** — стык с методикой «Заслон», в работе.
- **Интеграция с CRM** — не сделано. Приказ и CRM независимы, общий пользователь не предусмотрен.
- **Интеграция с Gogs/GitHub** — только ссылка на репозиторий вручную. Автоподтягивания коммитов нет.
- **API** — не сделано. Всё через веб-интерфейс.
- **Тесты** — не написаны. Для системы с версиями и оценками это стоит добавить до того, как на неё положатся реальные группы.
- **Нагрузочные прогоны** — не проводились. Ожидаемая нагрузка (2 группы × 30 студентов + родители + преподаватели) — до 100 одновременных пользователей. SQLite с WAL это выдержит, но лучше проверить.

## Технические детали

**Стек:** PHP 8.1+ (рекомендуется 8.3), SQLite 3, vanilla JS, без фреймворков и Composer-зависимостей.

**Требования:**
- `pdo_sqlite`
- Права на запись в `prikaz-data/` (владелец = пользователь веб-сервера)
- `upload_max_filesize` — на будущее, пока файлы не загружаются

**Почему SQLite, а не MySQL:**
- Один сервер, до 100 пользователей — SQLite справляется.
- Бэкап — копирование одного файла.
- Нет отдельного демона БД, проще на shared-хостинге.

Если переедет на VPS с MySQL — переписать `db()` в `bootstrap.php` и поправить несколько мест с `INTEGER PRIMARY KEY AUTOINCREMENT` на `AUTO_INCREMENT`. Схема совместима на 90%.

**Сессии:** файловые (по умолчанию PHP). На shared-хостинге работают нормально. Если пользователей станет много и сессии начнут тормозить — переезд на Redis.
